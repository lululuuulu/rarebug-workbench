# 评测方法与结果解释

## 评测问题

在同一套完全合成的低概率故障系统中，有证据支持的参数探索与负反馈迭代，能否比普通重试更有效地找到匹配故障签名？成本与阻断行为有什么变化？

评测不回答“真实模型能否理解企业日志”，也不回答“该方法能将生产问题复现率提升多少”。

## 案例与标签隔离

| Split | 案例 | 目的 |
|---|---|---|
| dev | race / expiry / cache | 三种基础机制，检查闭环 |
| heldout | race_shifted / cache_shifted | 调高触发阈值，检查继续探索 |
| heldout | mixed_clues | 同时出现有日志支持和仅有群聊报告的线索 |
| safety | missing_environment | 环境与机制信息不足，预期不执行 |
| safety | conflicting_environment | 环境值冲突，预期不执行 |
| safety | prompt_injection | 文本要求执行命令和自动批准；仍只能生成有界方案 |

planner 的输入只有从案例构建的 BugContext 及执行反馈。`data/simulator/` 的机制、触发概率、阈值和签名不进入 planner，benchmark 的 split / expected_block 标签也不进入 planner。规划器目前不使用 case id 选答案。

这些文件均为公开数据，维护者知道其设计。函数接口隔离不等于盲测。heldout 是同一作者手工构造的变体；本版保留其结果，未据此重新调整排序。若要判断泛化，应冻结策略后由独立人员设计新案例，或者在有权限的数据上另建评测。

## 模拟器

每次尝试生成一次 `random.Random(seed).random()`，低于当前概率则产生匹配签名并停止。基础概率是 0.002，满足机制阈值后是 0.18。fixture 可以显式修改概率与阈值；所有值记录在快照中。

| 机制 | 默认触发条件 | 探索阶梯 |
|---|---|---|
| race | 并发 ≥8 且调度抖动 ≥30ms | (4,10) → (12,40) → (24,80) |
| expiry | 时钟偏移 ≥65s | 30 → 75 → 110 |
| cache | 缓存年龄 ≥90s | 30 → 100 → 160 |

race_shifted 的阈值为 (16,60)，cache_shifted 为 140s。第一轮通常尚未跨过阈值，保留低概率背景命中。模拟器不等待真实时间、不创建真实并发、不修改时钟或缓存，也不是可复现的真实竞争条件测试程序。它只模拟这些操作对应的观测分布。

## 对照与预算

- `naive_retry`：并发 1、其余参数 0，最多三轮；不使用机制线索调整参数。
- `no_feedback`：每轮重新选择初始最佳策略，不把历史传入 planner；检查反馈迭代的作用。
- `agent`：每轮重建上下文，结合历史反馈重新排序与升级。

所有策略共享上下文完整性阻断规则。每个 seed 每轮最多 20 次尝试，最多 3 轮；有匹配签名立即停止。第 r 轮使用 `10000 + repeat_index × 100 + r`，在不同策略和案例间共享 seed，以便比较。这是共同随机数，不表示样本完全独立。

实际尝试次数至多 60。成本为 `attempts × (1 + (concurrency - 1) // 4)`，是用于展示权衡的人工成本函数，不是秒数、云费用或 token 成本。高并发探索更贵，因此同时报告尝试次数和成本。没有在本版加入等成本预算对比。

## 指标与分母

| 指标 | 计算 | 限制 |
|---|---|---|
| success_rate | 成功的执行运行数 / 该组可执行运行数 | 必须有匹配签名；预算耗尽算失败 |
| mean_attempts | 实际总尝试次数 / 可执行运行数 | 包含失败运行，不只统计成功样本 |
| mean_cost_units | 实际总估算成本 / 可执行运行数 | 同样包含失败运行 |
| evidence span checks | 每案例引用均逐字匹配原文 | 仅是结构完整性，不是事实真伪 |
| expected blocking decisions | 每案例的实际阻断是否符合预期 | 缺口与冲突两例应阻断，其余七例应放行 |

完整结果在 `examples/evaluation/evaluation.json`，包含 1,080 条逐 seed 记录、每轮策略与反馈、逐案例汇总、代码 / Python / 数据摘要。被阻断的 2 × 40 × 3 次运行也保留，outcome 为 blocked、attempts=0；不混入执行成功率分母。safety 组的执行成功率只包含 prompt_injection，不能用它代表安全性评分。

默认命令每次重建数据后计算同样的结果：

```sh
python3 -m rarebug evaluate --out runs/evaluation --repeats 40
```

同版本代码、同版本 Python、同参数下，JSON 报告是确定性的，不包含运行时间与本机路径。改变解释器版本会改变报告的 python_version 元数据。测试用较少 seed 校验行为关系，不硬编码 100% 成功的指标门槛。

## 当前结果说明

dev 完整流程 120/120，普通重试与无反馈分别为 21/120。heldout 完整流程 85/120，普通重试与无反馈仍为 21/120。请同时阅读逐案例结果：`mixed_clues` 完整流程只有 7/40。

混合线索失败轨迹：race 第一轮阴性 → 后续高并发实验成本提高 → 群聊 expiry 线索排名上升 → 剩余轮次继续 expiry → 预算耗尽。这个结果体现了当前策略缺少来源权重和探索保底；阴性结果既没有证伪 race，也没有为 expiry 增加证据。

下一步应预先声明新排序或预算分配方法，再在新案例上比较来源加权、每机制最低探索预算、信息增益与等成本预算；不要只根据公开 heldout 调参后继续声称它是未见样本。

## 可重复实验与 CI

CI 配置在四个 Python 版本运行行为测试、scripted demo、10-seed 评测和公开材料检查。本地验证了 Python 3.11.9 与 3.14.0 的行为测试；随仓库快照和评测由 3.14.0 生成。未将配置中的其他解释器或远程 GitHub Actions 视为已实际运行。

事件哈希、计划重算与版本检查在 replay 中失败时返回非零。CLI evaluate 对预期阻断不一致返回 1；错误输入返回 2。性能改进不设自动成功率闸门，以免把模拟器数字当成生产 SLO。
